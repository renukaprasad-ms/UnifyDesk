# WhatsApp Message State Model

Status: FROZEN FOR ROUND 1

## Inbound

Provider webhook -> durable event -> InboxMessage(RECEIVED).

Idempotency key:
(connection_id, provider_message_id)

Inbound lifecycle is not retried as a new visible message. Any media enrichment retry updates the same canonical message.

## Outbound local lifecycle

PENDING
- local request validated and clientRequestId reserved
- provider not yet confirmed

ACCEPTED
- Meta send endpoint returned provider message ID

SENT
- provider status webhook reports sent

DELIVERED
- provider status webhook reports delivered

READ
- provider status webhook reports read

FAILED
- definite local/provider failure with no successful higher state

UNKNOWN
- request outcome ambiguous after possible provider submission

## Generic Inbox mapping

Current InboxMessageStatus cannot represent all provider states.

Mapping:
- PENDING before provider acceptance may be persisted only after the provider call strategy chosen by B2; user API uses runtime status.
- ACCEPTED/SENT/DELIVERED/READ -> InboxMessageStatus.SENT
- FAILED -> InboxMessageStatus.FAILED
- UNKNOWN -> do not falsely mark FAILED if provider may have accepted; runtime status is authoritative.

F1 must show detailed WhatsApp status from WhatsApp response/runtime augmentation, not infer delivered/read from generic SENT.

## Monotonic order

Successful rank:
PENDING=0
ACCEPTED=10
SENT=20
DELIVERED=30
READ=40

Apply a success event only if its provider timestamp/rank does not regress known truth.

FAILED handling:
- a failure event newer than acceptance and belonging to same provider message can set FAILED unless a later successful terminal event already exists;
- late/older failure cannot overwrite READ;
- duplicate failure is no-op.

## clientRequestId

Generated by frontend for each logical user send.

Uniqueness:
(company_id, connection_id, client_request_id)

Same clientRequestId:
- return same logical message/result
- never submit again

New clientRequestId:
- represents a new user intent and may submit.

The UI must not automatically replace clientRequestId after UNKNOWN.

## Reply context

Outbound replyToMessageId is a local InboxMessage ID.
Backend:
- company/conversation scope check;
- obtain referenced provider external_message_id;
- send as Meta context.message_id only when valid.

## Template state

Template send is its own message_kind=TEMPLATE and follows same provider message lifecycle.

## Media state

Media send:
- validates local Media first;
- obtains provider media ID/upload;
- sends message;
- provider media upload failure before message submission is definite/retryable;
- ambiguity after message submission follows UNKNOWN rule.

## User-visible error categories

- POLICY_TEMPLATE_REQUIRED
- TEMPLATE_NOT_APPROVED
- CONNECTION_REAUTH_REQUIRED
- CONNECTION_ACTION_REQUIRED
- RATE_LIMITED
- PROVIDER_TEMPORARY
- PROVIDER_REJECTED
- MEDIA_INVALID
- SEND_AMBIGUOUS

No raw Graph error response is rendered.
